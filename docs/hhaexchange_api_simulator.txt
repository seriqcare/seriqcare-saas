Name:
  HHAExchange API Simulator

Purpose:
  Simulates Pennsylvania-focused HHAExchange workflows for:
    - OAuth 2.0 token acquisition
    - caregiver pre-registration
    - EVV visit submission (single and batch) and management
    - async TransactionId / EVVMSID status polling
    - claim upload and simulated processing
    - agency-level claim summary reporting
    - V5 outbound file generation (billing exceptions, processed visits,
      claim responses, remittance/payment)

Primary use case:
  Local integration testing for a care-management application without needing
  live access to the real HHAExchange platform.

Current runtime model:
  - Node.js application using Express
  - SQL Server backend accessed through the mssql driver
  - Persistent process model (not serverless)
  - Local mode and Azure SQL production mode supported via ENV switch

  2. WHAT THE API DOES NOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Implemented features:

  1. OAuth token endpoint
     - POST /identity/connect/token
     - Simulates client_credentials flow
     - Returns Bearer token with 30-minute lifetime

  2. Bearer-token protection on business APIs
     - /api/caregivers/*
     - /api/evv/*
     - /api/claims/*
     - Missing or malformed Authorization header returns 401

  3. Caregiver pre-registration workflow
     - A caregiver must exist before a visit can be submitted
     - Caregiver uniqueness is enforced per agency

  4. Pennsylvania EVV field model
     - AgencyTaxId (EIN format XX-XXXXXXX) — replaces old providerId
     - CaregiverCode — replaces old caregiverId
     - MedicaidNumber — replaces old patientId
     - ProcedureCode (5-char HCPCS) — replaces old serviceCode
     - Visit time model uses ISO 8601 UTC datetimes
     - PayerId lookup enforced through PayerCodes table
     - EVVMSID (HHAX- prefix) generated by simulator for submitted visits
     - TransactionId (TXN- prefix) generated per visit for async polling
     - scheduleId, all four location fields required per CMS EVV mandate

  5. Single EVV visit submission
     - POST /api/evv/visits
     - Returns TransactionId and EVVMSID at the top level of the response
       (mirrors real HHAeXchange async workflow)

  6. Batch EVV visit submission
     - POST /api/evv/visits/batch
     - Accepts 1–100 visit records per request
     - Returns per-record TransactionId, EVVMSID, success/failure

  7. TransactionId status polling
     - GET /api/evv/visits/transactions/:transactionId
     - Returns Status (Accepted | Rejected | Pending), EVVMSID, and visit data

  8. Visit lifecycle management
     - Create, retrieve single, list with filters
     - Update non-approved visits (visitEditReasonCode required)
     - Delete non-approved visits
     - Approve submitted visits

  9. Claim lifecycle management
     - Upload claim file metadata
     - Duplicate active claim prevention by agency + claim number
     - Simulated async processing via setTimeout
     - Retrieve single claim, list with filters
     - Retry rejected/pending claims
     - Agency summary aggregation

  10. V5 outbound file generator
      - scripts/generate_v5_file.py
      - Queries live DB; no hardcoded fallback data
      - Four record types: BX (billing exceptions), PV (processed visits),
        CR (claim response), RP (remittance/payment)
      - Pipe-delimited, CRLF line endings per HHAeXchange outbound spec
      - Header (H) and trailer (T) records with section counts

  11. Automated end-to-end smoke test
      - scripts/e2e-test.js — 17 test groups, 60+ assertions
      - Covers success paths and negative validation checks

    This file.

  src/db/

    caregiver-api.js

    e2e-test.js
      Full end-to-end verification script against the running API.
    generate_v5_file.py
      Python script that generates a V5 outbound file from the live DB.

  6. AUTHENTICATION MODEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Token endpoint:

  POST /identity/connect/token

Expected request content type:
  application/x-www-form-urlencoded

Required fields:
  grant_type=client_credentials
  client_id=<any string>
  client_secret=<any string>
  scope=api

Success response (200):
  {
    "access_token": "sim-token-XXXXXXXXXXXX",
    "token_type": "Bearer",
    "expires_in": 1800
  }

Failure behavior:
  - Missing required OAuth parameters → 400 invalid_request
  - Unsupported grant type (e.g. password) → 400 unsupported_grant_type

Protected business endpoints (require Authorization: Bearer <token>):
  /api/caregivers/*
  /api/evv/*
  /api/claims/*

Current auth implementation detail:
  The middleware validates the presence and format of the Bearer token string.
  It does not introspect, sign, or persist token state. Any string prefixed
  with "Bearer " is accepted.

How to call (curl):
  TOKEN=$(curl -s -X POST http://localhost:3000/identity/connect/token \
    -H "Content-Type: application/x-www-form-urlencoded" \
    -d "grant_type=client_credentials&client_id=my-client&client_secret=my-secret&scope=api" \
    | python -c "import sys,json; print(json.load(sys.stdin)['access_token'])")

  # then use in subsequent calls:
  curl -H "Authorization: Bearer $TOKEN" http://localhost:3000/api/evv/visits

  createVisitId()
    VIS- + 9 uppercase alphanumeric characters

  createClaimId()
    CLM- + 9 uppercase alphanumeric characters

  createEvvmsid()

Important distinctions:

  - EVVMSID       — HHAeXchange-assigned visit identifier (HHAX- prefix)

  - ExternalEVVMSID — optional inbound client identifier (must start with ~,
                       must be unique if sent)

  13. ARCHITECTURE AND IMPLEMENTATION PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Layering:

  src/config       Configuration loading and ENV validation
  src/db           Connection setup and SQL batch execution
  src/repositories All DB queries and row mapping
  src/routes       Request validation, business orchestration, HTTP responses
  src/utils        ID generation helpers

Connection pool pattern:
  Single lazy-initialized mssql pool, shared across all request handlers.
  Graceful shutdown via closePool() on SIGINT / SIGTERM.

Repository mapping pattern:
  Database column names (PascalCase) are mapped to camelCase response objects.
  DutyCodes and RejectionReasons stored as pipe-delimited text; mapped to
  arrays on read.

Async claim simulation pattern:
  Route writes pending claim synchronously, responds 202.
  Background setTimeout (1–4 s) mutates status to approved or rejected.

TransactionId pattern:
  Every created visit gets a unique TransactionId stored in HHA.Visits.
  GET /visits/transactions/:transactionId looks up the visit by this field and
  maps internal status → HHAeXchange status (submitted → Accepted, etc.).

Logging pattern:
  server.js logs [timestamp] METHOD /path for every incoming request.

Schema reset safety:
  schema.sql drops all HHA.* tables before recreating them.
  Running npm run db:setup on an existing database is safe but destructive
  (all visit/claim data will be lost and replaced with seed data).

  14. SETUP, RESET, AND LOCAL RUNBOOK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Prerequisites:
  - Node.js v18+
  - SQL Server running on localhost:1433, database SeriqCareDB
  - SQL login 'hr' with access to SeriqCareDB (or update .env)
  - Python 3 + pip install pyodbc  (only required for V5 generator)

First-time setup:

  1. Install Node dependencies
       npm install

  2. Confirm .env matches your SQL Server credentials
       DB_SERVER_LOCAL=localhost
       DB_PORT_LOCAL=1433
       DB_NAME_LOCAL=SeriqCareDB
       DB_USER_LOCAL=hr
       DB_PASSWORD_LOCAL=<your password>

  3. Apply schema and seed data (drops + recreates all HHA.* tables)
       npm run db:setup

  4. Start the server
       npm start

  5. Verify health
       curl http://localhost:3000/health

Schema-only migration (add missing columns without full reset):
  If schema.sql was updated after the DB was last set up, run the inline
  migration via Node directly, e.g.:
    node -e "
      const { getPool } = require('./src/db/connection');
      getPool().then(p => p.request().query(
        'ALTER TABLE HHA.Visits ADD TransactionId NVARCHAR(64) NULL'
      )).then(() => { console.log('done'); process.exit(0); });
    "
  Or just run npm run db:setup for a full reset.

Reset database state:
  Full schema reset + seed:   npm run db:setup
  Seed only:                  npm run db:seed

Run end-to-end verification (server must be running first):
  npm test

  16. KNOWN IMPLEMENTATION NOTES / GAPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are not blockers for E2E success but are useful to know:

  1. server.js /api/docs still contains some legacy providerId-style example
     payloads. The route handlers are correct; only the docs JSON is stale.

  2. claims-repository.js exports getProviderSummary and
     findActiveClaimByProviderAndNumber — names reflect the old providerId
     model but the underlying queries now use AgencyTaxId correctly.

  3. GET/PUT /api/caregivers/:caregiverCode identifies records by caregiverCode
     only. The DB key is composite (AgencyTaxId + CaregiverCode). In a
     multi-agency environment this could return or update the wrong record if
     the same caregiverCode exists under two agencies.

  4. updateVisit() in evv-repository.js does not update every optional field
     that createVisit() accepts (e.g. scheduleStartTime, scheduleEndTime,
     payerId, dutyCodes, missedVisit). Notes, status, and core datetime fields
     are updatable.

  5. The TransactionId column was added to HHA.Visits after the initial DB
     setup. If the column is missing (error: Invalid column name 'TransactionId')
     run: npm run db:setup   or apply an ALTER TABLE manually (see section 14).

  17. EXAMPLE LIVE FLOW — CALLING THE API
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Full PA EVV workflow (curl):

  # Step 1 — Acquire Bearer token
  TOKEN=$(curl -s -X POST http://localhost:3000/identity/connect/token \
    -H "Content-Type: application/x-www-form-urlencoded" \
    -d "grant_type=client_credentials&client_id=my-client&client_secret=my-secret&scope=api" \
    | node -e "process.stdin.resume();let d='';process.stdin.on('data',c=>d+=c).on('end',()=>console.log(JSON.parse(d).access_token))")

  # Step 2 — Register caregiver (must do this before submitting visits)
  curl -s -X POST http://localhost:3000/api/caregivers \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{
      "agencyTaxId": "23-1234567",
      "caregiverCode": "MY-CG-001",
      "firstName": "Jane",
      "lastName": "Doe",
      "caregiverType": "RN"
    }'

  # Step 3 — Submit a single EVV visit
  TODAY=$(date -d "yesterday" +%Y-%m-%d 2>/dev/null || date -v-1d +%Y-%m-%d)
  VISIT=$(curl -s -X POST http://localhost:3000/api/evv/visits \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d "{
      \"agencyTaxId\": \"23-1234567\",
      \"caregiverCode\": \"MY-CG-001\",
      \"medicaidNumber\": \"600012345\",
      \"procedureCode\": \"W7060\",
      \"payerId\": \"17470\",
      \"scheduleId\": \"SCHED-001\",
      \"scheduleDate\": \"$TODAY\",
      \"scheduleStartTime\": \"${TODAY}T09:00:00Z\",
      \"scheduleEndTime\": \"${TODAY}T10:30:00Z\",
      \"clockInDatetime\": \"${TODAY}T09:02:00Z\",
      \"clockOutDatetime\": \"${TODAY}T10:28:00Z\",
      \"clockInServiceLocationType\": \"Home\",
      \"clockInServiceLocationAddress\": \"123 Main St, Pittsburgh, PA 15213\",
      \"clockOutServiceLocationType\": \"Home\",
      \"clockOutServiceLocationAddress\": \"123 Main St, Pittsburgh, PA 15213\",
      \"dutyCodes\": [\"115\",\"120\"],
      \"externalEvvmsid\": \"~MY-VISIT-001\",
      \"notes\": \"Personal care services\"
    }")
  echo $VISIT | node -e "process.stdin.resume();let d='';process.stdin.on('data',c=>d+=c).on('end',()=>{const b=JSON.parse(d);console.log('TransactionId:',b.TransactionId,'EVVMSID:',b.EVVMSID)})"

  # Step 4 — Poll transaction status
  TX_ID=$(echo $VISIT | node -e "process.stdin.resume();let d='';process.stdin.on('data',c=>d+=c).on('end',()=>console.log(JSON.parse(d).TransactionId))")
  curl -s -H "Authorization: Bearer $TOKEN" \
    http://localhost:3000/api/evv/visits/transactions/$TX_ID

  # Step 5 — Submit a batch of visits
  curl -s -X POST http://localhost:3000/api/evv/visits/batch \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d "[
      {
        \"agencyTaxId\": \"23-1234567\", \"caregiverCode\": \"MY-CG-001\",
        \"medicaidNumber\": \"600012345\", \"procedureCode\": \"T1019\",
        \"payerId\": \"17470\", \"scheduleId\": \"SCHED-B1\",
        \"scheduleDate\": \"$TODAY\",
        \"scheduleStartTime\": \"${TODAY}T13:00:00Z\",
        \"scheduleEndTime\": \"${TODAY}T14:00:00Z\",
        \"clockInDatetime\": \"${TODAY}T13:01:00Z\",
        \"clockOutDatetime\": \"${TODAY}T13:59:00Z\",
        \"clockInServiceLocationType\": \"Home\",
        \"clockInServiceLocationAddress\": \"456 Oak Ave, Pittsburgh, PA 15202\",
        \"clockOutServiceLocationType\": \"Home\",
        \"clockOutServiceLocationAddress\": \"456 Oak Ave, Pittsburgh, PA 15202\",
        \"externalEvvmsid\": \"~MY-BATCH-001\"
      }
    ]"

  # Step 6 — Upload a claim
  curl -s -X POST http://localhost:3000/api/claims/upload \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{
      "agencyTaxId": "23-1234567",
      "claimNumber": "PA-9000001",
      "fileName": "claims_demo.csv",
      "fileFormat": "CSV",
      "claimAmount": 2750.00,
      "visitCount": 3,
      "claimPeriodStart": "2026-03-01",
      "claimPeriodEnd": "2026-03-31"
    }'

  # Step 7 — Check claim status
  curl -s -H "Authorization: Bearer $TOKEN" \
    http://localhost:3000/api/claims/CLM-XXXXXXXXX

  # Step 8 — Agency summary
  curl -s -H "Authorization: Bearer $TOKEN" \
    http://localhost:3000/api/claims/agency/23-1234567/summary

  # Step 9 — Generate V5 outbound file
  npm run v5 -- --agency 23-1234567
