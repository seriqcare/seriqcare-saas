You are a senior full-stack engineer. Implement a **Structured Documentation Template Builder** for my multi-agency home care SaaS called **SeriqCare**.

## Product context

SeriqCare is a multi-agency home care application. Different agencies use the same platform, so **strict agency isolation** is mandatory. One agency must never see another agency’s templates, submissions, patients, or staff data.

The feature to build is **Documentation Templates**. Agency admins should be able to create their own structured documentation templates without code, publish them, and let caregivers/staff fill them out during visits or for general care documentation.

This is **not** a pure WYSIWYG editor. It is a **structured template builder** with sections and fields. We may support a rich text instruction block, but the foundation must be structured fields.

## Goal

Build a production-ready first version of a **Structured Documentation Template Builder** with:

* template creation
* section-based template design
* configurable structured fields
* publish/unpublish workflow
* template versioning
* dynamic form rendering
* submission storage
* agency isolation
* role-based permissions
* audit-safe design
* clean, professional UI

## Tech assumptions

Use the stack below unless clearly impossible:

* Backend: FastAPI
* Database: SQL Server
* ORM/data access: SQLAlchemy
* Frontend web UI: server-rendered/Jinja2 + Bootstrap or clean professional CSS
* Mobile support: design the backend/API and JSON schema so Flutter/mobile can render the same templates later
* Authentication: use the existing SeriqCare auth patterns and current user / agency context
* Follow good modular architecture and avoid tightly coupled code

## Core business requirements

### 1. Agency isolation

Every template, template version, submission, and submission value must belong to an `agency_id`.
All queries must be scoped to the logged-in user’s agency unless explicitly global system data is intended.
Do not rely only on the UI for isolation. Enforce it in backend service/repository logic too.

### 2. Roles and permissions

Implement at least these permissions:

* Agency Admin:

  * create templates
  * edit draft templates
  * publish templates
  * archive templates
  * view all submissions for their agency
* Caregiver / Staff:

  * view templates assigned/available to them
  * create submissions
  * save drafts
  * submit completed documentation
* Supervisor/Admin:

  * review submitted documentation
  * read all agency submissions

If role model already exists, integrate with it. Otherwise implement a minimal permission check pattern.

### 3. Template builder

Agency Admin can:

* create a template
* set template name
* set description
* set category
* add sections
* reorder sections
* add fields inside sections
* reorder fields
* configure field settings
* save template as draft
* publish template
* archive template

### 4. Supported field types for v1

Implement these field types:

* short_text
* long_text
* number
* date
* time
* datetime
* dropdown
* radio
* checkbox
* yes_no
* signature_placeholder
* file_upload_placeholder
* instruction_block
* staff_selector
* patient_selector

Notes:

* `instruction_block` is display-only, not an input
* `signature_placeholder` and `file_upload_placeholder` can be implemented in an MVP-safe way if full signature/file capture is not yet completed
* `staff_selector` and `patient_selector` should integrate with agency-scoped staff/patient data
* all field types should share a consistent schema shape

### 5. Field configuration

Each field should support relevant config such as:

* `field_key`
* `label`
* `help_text`
* `placeholder`
* `required`
* `default_value`
* `options` for dropdown/radio
* `min_length`
* `max_length`
* `min_value`
* `max_value`
* `sort_order`
* `width` or layout hint if useful
* `is_active`

Do not overcomplicate the first version, but keep the schema extensible.

### 6. Template versioning

This is very important.

Requirements:

* A published template becomes immutable for active use
* If an admin edits a published template, create a **new version**
* Old submissions must remain tied to the old template version
* A submission must store both:

  * `template_id`
  * `template_version`
* It must remain possible to render historic submissions exactly as they were when completed

### 7. Submission workflow

Staff should be able to:

* open a template
* fill it dynamically
* save as draft
* submit when complete

Statuses for submissions:

* draft
* submitted
* reviewed (optional for v1 if easy)
* approved (optional for v1 if easy)

On submit:

* validate required fields
* validate field types
* store values safely
* block cross-agency access

### 8. Assignment model

Design the system so templates can later be assigned by:

* service
* program
* visit type
* patient
* payer workflow

For v1, it is okay to keep assignment simple, such as:

* manual availability by agency
* optional category
* optional “usable during visit documentation”

But structure the code so later assignment rules can be added cleanly.

## JSON schema expectations

### Example template schema

Use a consistent JSON structure like:

```json
{
  "template_name": "Daily Care Note",
  "category": "progress_note",
  "version": 1,
  "sections": [
    {
      "key": "visit_information",
      "title": "Visit Information",
      "sort_order": 1,
      "fields": [
        {
          "key": "visit_date",
          "type": "date",
          "label": "Visit Date",
          "required": true
        },
        {
          "key": "start_time",
          "type": "time",
          "label": "Start Time",
          "required": true
        }
      ]
    },
    {
      "key": "observations",
      "title": "Observations",
      "sort_order": 2,
      "fields": [
        {
          "key": "mood",
          "type": "dropdown",
          "label": "Mood",
          "required": false,
          "options": [
            {"label": "Calm", "value": "calm"},
            {"label": "Anxious", "value": "anxious"},
            {"label": "Agitated", "value": "agitated"}
          ]
        },
        {
          "key": "notes",
          "type": "long_text",
          "label": "Notes",
          "required": true
        }
      ]
    }
  ]
}
```

### Example submission values

```json
{
  "visit_date": "2026-04-06",
  "start_time": "09:00",
  "mood": "calm",
  "notes": "Patient was stable and cooperative."
}
```
