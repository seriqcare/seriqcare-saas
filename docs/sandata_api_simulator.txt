PA SANDATA ODP EVV SIMULATOR — IMPLEMENTATION DETAILS
======================================================

Purpose
-------
This simulator implements PA Sandata Alternate EVV workflow for ODP payloads
with the required processing sequence:

1. Client payloads
2. Employee payloads
3. Visit payloads

Claims processing has been fully removed from server routes, repository logic,
schema usage, seed data, docs, and test flow.

Architecture
------------
- Runtime: Node.js + Express
- Database: SQL Server (`SANDATA` schema)
- Entry point: `server.js`
- Route layer: `src/routes/evv-api.js`
- Repository layer: `src/repositories/evv-repository.js`
- Config layer: `src/config/env.js`

Environment Modes
-----------------
Runtime mode is controlled by `ENV` in `.env`:

- `ENV=local`
	- SQL authentication mode
	- Variables: `DB_SERVER_LOCAL`, `DB_PORT_LOCAL`, `DB_NAME_LOCAL`, `DB_USER_LOCAL`, `DB_PASSWORD_LOCAL`

- `ENV=production`
	- Azure SQL + Azure AD service principal mode
	- Variables: `DB_SERVER`, `DB_PORT`, `DB_NAME`, `DB_CLIENT_ID`, `DB_CLIENT_SECRET`, `DB_TENANT_ID`

Data Model
----------
Tables created by `sql/schema.sql`:

- `SANDATA.sandata_clients`
- `SANDATA.sandata_employees`
- `SANDATA.sandata_visits`
- `SANDATA.sandata_submission_log`
- `SANDATA.sandata_response_log`

Repository Behavior
-------------------
`src/repositories/evv-repository.js` provides:

- Upsert-style persistence for client/employee/visit entities
- Reads by business keys:
	- client: `ClientIdentifier`
	- employee: `EmployeeIdentifier`
	- visit: `VisitOtherId`
- List endpoints for all entities
- Submission/response audit log persistence and retrieval

Submission Response Contract
----------------------------
Submission endpoints return Sandata-style record processing summaries:

- `Status`: `SUCCESS` or `FAILED`
- `Message`: contextual processing message
- `RecordCount`: number of processed records
- `Records`: per-record status array
	- `SequenceID`
	- `RecordStatus` (`SUCCESS` or `FAILED`)
	- `RecordError` (includes validation text and ESC code on failure)

Single and bulk payloads are both supported, and bulk submissions can produce mixed
success/failure `Records` in one response.

Validation and ESC Logic
------------------------
Validation is applied per record for client, employee, and visit payloads.
Failures are returned as per-record `RecordError` values including ESC codes.

Implemented ESC mappings:

- `ESC-601` Missing Call-In or Call-Out
- `ESC-602` Visit duration is zero or negative
- `ESC-603` Invalid or unmapped Procedure Code/Modifier
- `ESC-604` Client not found in DHS Aggregator (dependency check)
- `ESC-605` Employee not found in DHS Aggregator (dependency check)
- `ESC-606` Visit outside authorized service window (internal processing fallback)
- `ESC-607` Invalid Payer or Program for PA ODP
- `ESC-609` Invalid Employee PIN
- `ESC-611` Missing Reason Code for manual edits

Examples of implemented rule checks:

- Client
	- `ClientQualifier` must be `ClientCustomID`
	- `ClientIdentifier` and `ClientMedicaidID` must be 10 digits
	- `PayerID=PAODP`, `PayerProgram=ODP`

- Employee
	- `EmployeeQualifier` must be `EmployeeCustomID`
	- `EmployeeSSN` must match `0000#####` pattern
	- PA-disallowed employee fields are rejected

- Visit
	- Requires existing client and employee records before acceptance
	- Manual/no-call visits require adjusted in/out timestamps
	- Call segments enforce call-type requirements
	- Visit changes enforce reason code requirements

Client General Fields

- ClientQualifier: required, must be "ClientCustomID"

- ClientFirstName: required, max 30
- ClientMiddleInitial: optional, max 1

- ClientTimeZone: required, e.g. "US/Eastern"

Database Setup and Seed Behavior
--------------------------------
Scripts:

- `npm run db:setup` runs `sql/schema.sql` then `sql/seed.sql`
- `npm run db:seed` runs `sql/seed.sql` only

Current `sql/seed.sql` behavior:

- Clears data before insert
- Uses FK-safe reset order:
	- `TRUNCATE`: response log, submission log, visits
	- `DELETE`: employees, clients
- Inserts baseline sample client, employee, and visit records

Test Runner Behavior
--------------------
`client.js` is the end-to-end API test process.

Scripts:

- `npm run test:api`
	- Non-strict mode by default
	- Does not return non-zero exit code for record failures

- `npm run test:api:strict`
	- Strict mode
	- Returns non-zero exit code on failures

Additional safeguards in test runner:

- Detects wrong target service via `/health` response
- Aborts early if `BASE_URL` points to a different app
- Truncates large string/HTML payload output to prevent terminal flooding

Recommended invocation when multiple local apps are running:

- `set BASE_URL=http://localhost:3002`
- `npm run test:api`

Current Project Scope
---------------------
This repository now represents an EVV-only PA ODP Sandata simulator with:

- EVV submission and retrieval APIs
- Sandata-style submission result envelopes
- ESC-coded validation failures per record
- Audit logging for outbound payloads and processed results
- Local and production (service principal) environment support
